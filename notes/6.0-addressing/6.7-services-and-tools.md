# 6.7 TCP/IP Services and Tools

Section **6.0 Addressing**. Port numbers are in 3.1. This note is what the services are for, and the commands that show whether they are working.

## Services beyond the port table

| Service | What it actually does |
|---|---|
| DHCP | Leases addresses (6.4) |
| DNS | Names (6.5) |
| NTP | Keeps clocks close enough for Kerberos, logs, and certificates. UDP 123 |
| SNMP | A manager polls agents (UDP 161) and receives traps (UDP 162). Use version 3 |
| Syslog | Devices ship log lines to a collector. UDP 514, or TCP when you cannot afford to lose them |
| SMTP, POP3, IMAP | Mail. See 3.1 |
| HTTP, HTTPS | The web, and a great deal of API traffic that is not a browser |
| FTP, SFTP, TFTP | File copy. TFTP has no login and is for boot images and device configs |
| SSH, Telnet, RDP | Remote administration. SSH and RDP. Not Telnet |
| LDAP | The directory behind logins |
| SMB, NFS | File shares |

A **well-known service on a moved port** still works, and every client and every firewall rule has to be told. Security by obscurity is not a control. It is a way to confuse your own documentation.

## Tools

These ask the stack a question. They do not fix it.

| Tool | Question it answers |
|---|---|
| `ping` | Does ICMP echo reach that address, and what is the round trip? Failure can mean the host is down **or** that ICMP is filtered. A few lost replies and a stable RTT is different from RTT that swings all over the place |
| `traceroute` / `tracert` | Which hop stops answering? TTL climbs from 1. Unix usually sends UDP. Windows sends ICMP. A row of stars often means that hop does not generate ICMP time-exceeded, not that the hop is down |
| `pathping` | Traceroute plus loss at each hop, after it has watched for a while |
| `ipconfig` / `ip addr` | What address, mask, and gateway did this host actually get? `ipconfig /all` shows DNS and DHCP too |
| `ipconfig /release` then `/renew` | Drop the lease and ask again. The test after you fix the DHCP server |
| `nslookup`, `dig` | What does DNS say, and which server said it? `dig +trace` shows the walk from the root |
| `arp -a` | The IPv4-to-MAC table. A wrong MAC here is a local delivery problem, not a routing problem |
| `route print`, `ip route` | Which gateway will be used for which destination. Two default routes are a common self-inflicted loop |
| `netstat`, `ss` | Which ports are listening, and which connections are established or stuck in CLOSE-WAIT or SYN-SENT |
| `nmap` | Which ports on a host answer. Use it on networks you are allowed to test. A scan is visible and is not a polite thing to aim at a network you do not operate |
| `tcpdump`, Wireshark | The packets themselves. Filter on the host and the port before you capture the whole VLAN |
| `telnet host 443` or `nc` | Does the TCP handshake to that port complete? The garbage you get back from HTTP is fine. "Connection refused" means nothing is listening. A hang means a filter is dropping the SYN |

## How to chain them

1. `ip addr` — do I have a real address, not 169.254, and a gateway?
2. `ping` the gateway, then a public address — is it local, or is it past the router?
3. `ping` a name — if the address works and the name does not, it is DNS.
4. `traceroute` when the gateway answers and the far side does not — find the last hop that does.
5. `ss` or a capture when the path works and the application still fails — look at the port and the TCP state.

Swapping step 1 and step 5 is how an afternoon disappears into a packet capture of a PC that never got a DHCP lease.
