# 13.1 QUIC, HTTP/3, and MACsec

Section **13.0 Current practice**. TCP and TLS are in 4.2 and 10.2. IPSec is in 10.2. This note is the transport and the link encryption that showed up after those chapters were written.

## QUIC

**QUIC** is a transport protocol on **UDP**, usually **port 443**. Encryption is part of the protocol (TLS 1.3), so there is no cleartext QUIC the way there is cleartext TCP. A firewall that allows only TCP 443 does not allow QUIC. A firewall that allows UDP 443 does.

What you gain, compared with a new TCP connection plus a TLS handshake:

| Property | What it means |
|---|---|
| Shorter setup | The cryptographic handshake and the transport handshake are one exchange. A resumed session can send data in the first flight (0-RTT) when the risk of a replay is acceptable |
| Many streams | One connection carries many independent streams. A lost packet stalls only the stream whose data was lost |
| Connection migration | The connection is identified by a connection ID, not only by the IP and port. A phone moving from Wi-Fi to cellular can keep the session |
| Encrypted transport headers | Middleboxes see UDP. They do not see sequence numbers, acknowledgements, or the streams |

The cost is visibility. A packet capture shows UDP 443 and little else unless you have the keys. Operations teams who lived on TCP retransmits in Wireshark have to use the application's own metrics, or a capture with TLS secrets, to see loss.

QUIC is also easy to break by accident. Some guest networks and older firewalls block UDP 443. Clients then fall back to TCP. If the fallback is slow, the user blames the application. Allow UDP 443 on purpose when the application is HTTP/3, and watch the fallback rate.

## HTTP/3

**HTTP/3** is HTTP semantics running on QUIC. The methods, URLs, and status codes are the same HTTP you already know.

| Version | Rides on |
|---|---|
| HTTP/1.1 | TCP, one request at a time per connection unless you open several connections |
| HTTP/2 | TCP, many streams, and one lost packet can stall every stream on that connection |
| HTTP/3 | QUIC, many streams, loss stalls only the affected stream |

A browser may try HTTP/3 and fall back. The DNS hint is often an HTTPS record or an `Alt-Svc` header, not a new port. Port 443 stays the number you filter. The transport under it is what changed.

## MACsec

**MACsec** (IEEE **802.1AE**) encrypts an Ethernet frame on one hop. The source and destination MAC addresses stay in the clear so a switch can still forward the frame. The payload, and usually the Ethertype, are encrypted and authenticated.

Keys are agreed with **MKA** (MACsec Key Agreement), which uses 802.1X. Both ends of the link must run it. A frame that fails the check is dropped on that link.

| | MACsec | IPSec | TLS |
|---|---|---|---|
| Layer | Hop by hop, layer 2 | Network path, layer 3 | The application session |
| Who can read the payload | The next MACsec peer, after it decrypts | The IPSec peer at the end of the tunnel | The TLS endpoint |
| Typical use | Switch-to-switch, host-to-switch, a WAN router hop you do not want sniffed | Site-to-site and remote access (8.3, 10.2) | HTTPS, and anything else that speaks TLS |

MACsec protects the cable and the adjacent device. Once the next hop decrypts the frame and routes it, protection ends unless the following hop has MACsec too, or a higher layer encrypts. It does not replace TLS on the web server. It replaces "anyone with a tap on this fiber can read the frames."
