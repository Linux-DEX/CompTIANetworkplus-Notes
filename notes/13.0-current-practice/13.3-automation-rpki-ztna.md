# 13.3 Automation, RPKI, and ZTNA

Section **13.0 Current practice**. Playbooks and infrastructure as code are in 12.2. SNMP is in 9.3. BGP is in 7.3. VPNs and zero trust are in 8.3 and 12.2. This note is the model-driven way to talk to a device, how the Internet checks a BGP announcement, and how a user reaches one application.

## YANG

**YANG** is a modeling language. It describes a device's configuration and its operational state as a tree: interfaces, VLANs, BGP neighbors, counters. It is a schema. It does not push a config by itself.

Two families show up in practice. **IETF** models are the standards-track ones. **OpenConfig** models are the ones a lot of multi-vendor automation actually targets. A tool can talk to two vendors only where both implement the same model. A vendor-only model works, and it locks the playbook to that vendor.

## NETCONF and RESTCONF

Both protocols edit and read the YANG tree. The difference is the shape of the API.

| | NETCONF | RESTCONF |
|---|---|---|
| Transport | SSH, usually **TCP 830** | HTTPS |
| Payload | XML | JSON or XML |
| Style | RPC: get-config, edit-config, commit, lock | REST: GET, PATCH, PUT, DELETE on a URL that is the YANG path |
| Why it exists | A full configuration transaction, with a candidate config you can commit or discard | People who already automate with HTTP |

The useful NETCONF idea is the **candidate** datastore. You edit a copy, validate it, then commit it to running. A bad edit does not have to become the forwarding state. A lock stops two tools from committing over each other.

RESTCONF is the same tree over HTTP. It fits infrastructure-as-code tools and scripts. It is a poor choice on a management plane that is reachable from the user VLAN. Put it on the out-of-band path (12.4), with a real certificate.

## Streaming telemetry

SNMP polls. The manager asks, the device answers, and the gap between polls is time you did not see (9.3).

**Streaming telemetry** has the device **push** measurements on a timer or on a change. The data is structured with a YANG model, so "interface errors" is a named leaf, not a private OID you hope you decoded. **gNMI** over gRPC is the common dial. A collector subscribes. The device sends updates.

| Choice | Consequence |
|---|---|
| A short interval on every counter | You will see bursts, and you will also fill the collector and the management link |
| On-change for state, a slower interval for counters | The usual compromise |
| No subscription filter | The device exports the whole model. Start from the signals you already alert on (12.4's list: errors, drops, BGP state, power) |

Telemetry does not page a human. The collector and the alert still have to exist. A stream nobody watches is a more expensive SNMP.

## RPKI

**RPKI** (Resource Public Key Infrastructure) is the address registry's way of signing "this autonomous system may announce this prefix." The regional registries issue the certificates. The object you publish is a **ROA** (Route Origin Authorization): a prefix, a maximum prefix length, and the origin AS that is allowed to announce it.

Routers that do **route origin validation** compare each BGP announcement to the ROAs.

| Result | Meaning | Usual action |
|---|---|---|
| Valid | The origin AS matches a ROA | Accept |
| Invalid | A ROA exists and this origin is not it, or the prefix is longer than the ROA allows | Drop, if you have chosen to enforce |
| NotFound | No ROA covers this prefix | Accept. Much of the table is still in this state |

Publish ROAs for your own prefixes, including the length you actually announce. A ROA with a max length of /24 while you announce a /24 from a different AS than the ROA names will make your own route Invalid. That outage is self-inflicted and it is the main operational surprise.

RPKI checks the **origin**. It does not, by itself, stop a leak where the authorized AS is still the origin and someone in the middle is forwarding the route the wrong way. It does stop the common hijack where a stranger's AS originates your prefix.

## ZTNA

**ZTNA** (Zero Trust Network Access) connects a user to an **application**, after checking identity and the device. A VPN connects a user to a **network** (8.3). That is the whole design difference. Zero trust as a principle is in 12.2. ZTNA is the product shape of that principle for remote access.

The usual pieces:

| Piece | Role |
|---|---|
| Client or browser | The user. A clientless session covers web apps. A client covers thick apps |
| Broker / controller | Authenticates the user, checks posture (patched, encrypted disk, a managed device), and decides which applications this identity may open |
| Connector | Sits next to the application and calls out to the broker. The application does not need a public address |
| Policy | Names the application, not a subnet. "Finance app, these groups, these device checks" |

Traffic to anything else is not routed onto a LAN. A stolen laptop that passes no posture check does not land inside `10.0.0.0/8`.

ZTNA is one of the security services inside SSE and SASE (12.2). You can buy it without buying the SD-WAN half. The failure mode is the broker and the identity provider: if they are down, the applications that depend on them are down, so they need the same care as a VPN concentrator.
