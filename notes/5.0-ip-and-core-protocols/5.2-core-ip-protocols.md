# 5.2 IP, UDP, ARP, ICMP, and IGMP

Section **5.0 IP and Core Protocols**. TCP, which is the reliable transport on top of IP, is 4.2. This note is everything else in that original "IP addresses" file, at the depth the protocols actually need.

## IP

**Internet Protocol** delivers a packet from a source address to a destination address across a series of routers. It is **connectionless** (no handshake, no state about your flow) and **best effort** (no retransmission, no order, no promise the packet arrives). Reliability is TCP's job, or the application's.

What IP itself defines:

- The header layout, including the source and destination addresses.
- How a router chooses a next hop (the forwarding half of routing; building the table is a routing protocol).
- Fragmentation, when a packet is larger than the next link's MTU.
- A **protocol number** that says what is inside: ICMP 1, IGMP 2, TCP 6, UDP 17, GRE 47, ESP 50, AH 51, OSPF 89.

### IPv4 header fields worth naming

The header is 20 bytes unless options are present.

| Field | Why it exists |
|---|---|
| Version | 4 or, in an IPv6 header, 6 |
| IHL | Header length. Options make it larger than 5 words |
| DSCP / ECN | QoS marking, and a congestion signal (4.2) |
| Total length | Header plus payload, up to 65535 |
| Identification, flags, fragment offset | Reassembly of fragments. The Don't Fragment flag is how path MTU discovery works |
| TTL | Hop limit. Each router subtracts 1. At 0 the packet is dropped and ICMP time-exceeded is sent. This is what `traceroute` provokes, and what kills a routing loop |
| Protocol | The number from the list above |
| Header checksum | The IPv4 header only, not the payload. IPv6 dropped it |
| Source and destination | The addresses from 5.1 |

A router forwards on the destination. It does not care about TCP ports unless it is also doing NAT or filtering.

## UDP

**User Datagram Protocol**, IP protocol 17, is the transport you use when the application wants speed and small messages more than it wants a connection. DNS, DHCP, NTP, SNMP, syslog, and voice media all sit here.

The header is **8 bytes** and then the payload:

| Field | Size |
|---|---|
| Source port | 16 bits |
| Destination port | 16 bits |
| Length | 16 bits, header plus data |
| Checksum | 16 bits, over a pseudo-header plus UDP. In IPv4 it may theoretically be 0 ("no checksum"). In IPv6 it is required |

Properties, all of them deliberate:

- **No connection.** No handshake, no teardown, no state.
- **No retransmission.** A lost datagram stays lost. The application retries if it cares (DNS asks again).
- **No ordering and no flow control.**
- **Datagram boundaries are preserved.** One send is one receive. This is the opposite of TCP's byte stream.
- **The checksum** catches corruption. It does not cause a retry. A failed checksum means the datagram is discarded.
- A host can send as fast as it wants, which will bully TCP flows that politely back off. That is a reason to rate-limit UDP, not a reason to avoid it for DNS.

VoIP and games prefer a missing packet to a retransmitted one that arrives 200 ms late and misses its playback slot. TCP would hide the loss and add the delay. UDP lets the codec conceal the gap.

## ARP

**Address Resolution Protocol** answers: "I have an IPv4 address on my subnet; what MAC address should the Ethernet frame use?"

IP does not travel by itself on Ethernet. The frame needs a destination MAC. If the IP is on another network, the MAC you need is the **gateway's**, not the final host's. The host learns that from its routing table (default route) and then ARPs for the gateway.

The exchange:

1. The sender looks in its **ARP cache** for the IP.
2. On a hit, it uses the cached MAC and is done.
3. On a miss, it broadcasts an ARP request: "Who has 192.168.1.10? Tell 192.168.1.5." Destination MAC is `FF:FF:FF:FF:FF:FF`. EtherType is `0x0806`.
4. The owner answers with a **unicast** ARP reply containing its MAC.
5. The sender caches the mapping and transmits.

Entries age out (often a few minutes) so a replaced NIC does not stay wrong forever. A static ARP entry does not age out, which is useful and is also a way to break things if you typo it.

**Gratuitous ARP** is a host announcing its own IP-to-MAC mapping, unsolicited. Hosts do it when an address comes up, to detect duplicates and to refresh neighbors' caches. Attackers do it to poison those caches. The frame looks the same; the intent does not.

**RARP** (reverse ARP) was "my MAC is this; someone please tell me my IP". It needs a RARP server and it was replaced by BOOTP and then DHCP. You may see the name. You will not deploy it.

ARP is IPv4 only. IPv6 uses **Neighbor Discovery** (ICMPv6) for the same job.

## ICMP

**Internet Control Message Protocol**, IP protocol 1, is how IP reports problems and how a few diagnostic tools work. It is a payload of IP, not a transport, and it has **no ports**. Filtering "ICMP" is not the same as filtering a TCP port.

The header starts with a **type** and a **code**.

| Type | Name | Who uses it |
|---|---|---|
| 0 | Echo reply | Ping's answer |
| 3 | Destination unreachable | A router or the host cannot deliver. The code says why: network, host, port, or fragmentation needed (code 4, path MTU) |
| 5 | Redirect | A router telling a host "use that other router". Rarely welcome on a secured LAN |
| 8 | Echo request | Ping |
| 11 | Time exceeded | TTL hit 0 (code 0), which is traceroute, or fragment reassembly took too long (code 1) |

**Ping** sends an echo request and waits for an echo reply. Success means IP reached that address and the reply reached you. Failure does not always mean the host is down: something in the path may drop ICMP and still pass TCP.

**Traceroute** sends packets with TTL 1, then 2, then 3. Each router that decrements the TTL to 0 replies with time-exceeded, so you learn the hop. Unix typically sends UDP to a high port. Windows `tracert` sends ICMP echo. `pathping` combines traceroute with per-hop loss statistics.

ICMP is also the error path for "administratively prohibited" and for "packet too big". A firewall that drops all ICMP breaks path MTU discovery (4.2) and makes failures harder to diagnose. Filter the dangerous types (redirects from the outside) and let the useful ones through.

## IGMP

**Internet Group Management Protocol**, IP protocol 2, is how a host tells its local router "I want multicast group 239.1.1.1" or "I am done with it". Routers use those reports to decide which groups to forward onto the LAN. Without IGMP, a router would have to flood every multicast, or forward none.

Switches that understand **IGMP snooping** listen to the same reports and send the group only to ports that asked. A switch that does not snoop floods multicast like broadcast.

Multicast addresses are 224.0.0.0/4 (5.1). `224.0.0.1` means every host on the subnet. `224.0.0.2` means every router. Those two do not need a join; they are link-local groups.

IGMP is not a routing protocol. PIM and the others move multicast *between* routers. IGMP only covers the last hop, between the host and its router.
