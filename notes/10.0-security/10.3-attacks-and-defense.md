# 10.3 Attacks and What They Do

Section **10.0 Security**. This is recognition and defense. It is not a procedure for carrying any of these out.

An attack against a network falls into a few effects: steal credentials, pretend to be someone else, read traffic, change traffic, or make the service unavailable. The names below are the ones the course uses for those effects.

## Availability: denial of service

A **denial of service** exhausts something the service needs: bandwidth, connection slots, CPU, or disk. Users see a timeout. A **distributed** denial of service comes from many sources at once, so blocking one address does not help.

| Name | Effect | What actually helps |
|---|---|---|
| Volumetric flood | The link is full of junk. Legitimate packets never get on it | Capacity and filtering upstream, at the ISP or a scrubbing service. Your firewall cannot drop packets that already filled the circuit |
| SYN flood | Half-open TCP handshakes fill the server's table | SYN cookies, and a limit on half-open connections. See the handshake in 4.2 |
| Application exhaustion | The requests look legitimate and are expensive to answer (a search, a login) | Rate limits, a challenge, capacity. Harder than a flood because the packets are well formed |
| Reflection / amplification | Small requests to a service that answers with a large reply, aimed at the victim by a spoofed source | Stop spoofed sources at your own edge (don't send packets whose source is not yours), and don't run open resolvers. You cannot configure the attacker's reflector |
| Resource lock | One account locked by repeated failures, or a process stuck | Lockout policies that do not let an outsider lock every account, and service limits |

Detect it by the baseline (9.1): utilization, connection counts, and logs that do not match Tuesday. Respond by preserving service (upstream filter, a sinkhole for traffic you can identify, a fail-over) and by keeping logs. Do not "test it" against a network you do not operate.

## Spoofing and on-path attacks

| Name | What the user experiences | Defense |
|---|---|---|
| IP spoofing | Packets claim a source they are not. Used to hide, or to abuse trust in an address | Ingress filtering. Do not allow your users to send addresses they do not own. Do not trust an IP address as an identity |
| ARP spoofing | On the local LAN, traffic for the gateway is delivered to the wrong MAC | Dynamic ARP inspection on the switch, and the knowledge that a flat VLAN makes this easy |
| DNS spoofing | A name resolves to the wrong address | DNSSEC where you can, and resolvers that are not open to the world. Check that your clients use your resolver |
| Evil twin | A Wi-Fi network with your SSID and no real authentication | 802.1X. A shared passphrase cannot tell a real AP from a second one using the same passphrase |
| On-path (man in the middle) | Someone relays the session and can read or change it | TLS with certificate checks the user does not click through. SSH host-key checking. Do not disable either because it was inconvenient once |
| VLAN hopping | A frame ends up in a VLAN the sender is not in | Don't negotiate trunks on access ports. Don't use a native VLAN that carries user traffic (7.4) |
| MAC flooding | The switch's MAC table fills, and it starts flooding frames out every port like a hub. The attacker on one port can then read traffic that should have stayed on another | Port security: a limit on how many MACs a desk port may learn (12.5) |
| Rogue DHCP | Clients get a gateway the attacker controls | DHCP snooping. The switch only accepts DHCP offers on ports you have marked as trusted |
| Rogue AP | An access point you did not install, bridged into your LAN | 802.1X so the AP's port authenticates, and a wireless IDS that notices a BSSID you do not own (10.4) |

## Credentials and people

| Name | Effect | Defense |
|---|---|---|
| Phishing | The user hands over a password or runs a payload they were sent | Mail filtering, MFA so the password is not enough, and a way for users to report it that someone reads |
| Password spraying | A few common passwords tried against many accounts, slowly, to avoid lockout | MFA, and monitoring for many failures across many accounts |
| Credential reuse | A password from another site works here | MFA, and a ban on shared accounts |
| Tailgating | A person follows someone through a door | See 10.5 |
| Shoulder surfing | Someone reads a password or a screen by standing where they can see it | Privacy filters, and a habit of locking the screen. No firewall sees this |
| Dumpster diving | Someone reads what you threw away: diagrams, password slips, old configs | Shred paper. Wipe disks. A config in the trash is still a config |
| Insider | Someone who is allowed in misuses that | Least privilege, logging, and separation of duties. A network cannot tell a malicious admin from a busy one if both use the same all-powerful account |

Malware names (virus, worm, trojan, ransomware, botnet) describe how it spreads and what it does, not a special network protocol. The network symptoms are command-and-control traffic, unusual DNS, and data leaving in a volume the user does not generate. Egress filtering and DNS logs catch more of this than a rule that blocks "hackers".

## What to do when you see one

Identify scope, contain (isolate the host or the VLAN, do not immediately reimage if you need the disk), keep the logs, and follow the incident process your organization actually has. Preserving evidence is 10.5. Inventing a response during the incident is how evidence gets wiped and the still-open path stays open.
